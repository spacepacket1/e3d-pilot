## 1. Goal and non-goals

**Goal.** A user's own agent can (a) fetch a skill from Pilot as clearly labelled data and apply it itself, (b) with the user's permission, note that it was used and how it went, (c) read the user's own honest track record: counts, an interval, sample size, source mix. Everything stays on the user's machine.

**Non-goals.** Pilot never runs, installs or enforces a skill here. No prompting for outcomes (ADR-0016; the opt-in reminder is out of scope, D5). No pooling, sharing, export or network (ADR-0020). No claim that a skill improves results, no ranking, no recommendation (L1+ is phase 6). No hosted/HTTP tools (phase 4; `skillsFrom` already refuses `E3D_MCP_SKILLS=1` on HTTP, `lib/mcp/skills-config.js:11`). No prediction capture, so `calibration` and `baseline` stay null (`lib/calibration/record.mjs:94-95`). No change to the existing four skill tools' names or output with the new flag off.

## 3. The use_id

**Issuer and format.** The stdio server issues it inside `e3d_get_skill`, never the client: `use_` + 32 hex from `crypto.randomBytes(16)` (the store's id rule is `^use_[0-9a-zA-Z]{4,40}$`, `store.mjs:410`; the observer path uses 20 hex, `lib/skills/observer.mjs:260`).

**Binding.** On issue the server keeps an **in-memory ledger** entry (never on disk): `{ use_id, session_id, skill:{id,version,definition_hash}, task_class, issued_at }`. `session_id` is 8 random bytes created at process start (one stdio process is one host session). The hash is the one of the definition actually served in that response. No disk write happens at issue, so a fetch alone leaves no trace (the user's permission is needed to persist anything, section 4).

**Persisting.** (Amended after review, B1: after a use is persisted the server never returns the `use_id` to the agent again; `report_use`, `report_outcome` and reads answer with the skill identity only, so the agent cannot hand a persisted id to a shell command. The human sees ids only in the CLI.) Only `e3d_skill_report_use` / `e3d_skill_report_outcome` write the use row, built **from the ledger entry, not from client input**, via `newUse` (`store.mjs:311`) with `mode: host_chat`, `host.family` = slug of the client's `clientInfo.name` (else `unknown-host`), `host.model_family` `unknown`, `task_class_source` `declared`/`none`, `run_ref` null, `issued_at` = ledger time, `expires_at` = +90 days (`USE_DAYS`, `store.mjs:23`). It goes through `registerUse` (`store.mjs:333`), which already refuses a same-id different-content use (`judgeUse`, :322-331).

**Expiry.** A ticket is valid for 24 hours **within its session** (`expires_in_hours`: D6); after that or in another process: `skill_use_not_found` (the ledger is empty). The persisted row keeps the store's 90-day id life and 365-day retention; the later `--report-outcome` CLI works on a persisted use from any session, by the human.

**Replay and forgery.** (a) An invented, foreign-session or other-user id is not in the ledger: same error `skill_use_not_found` for all, no oracle. (b) The same report twice is `unchanged` (`appendOutcome` idempotence, `store.mjs:386`). (c) A different result for the same use is a supersession with `supersedes` naming the current outcome (`reportOutcome`, `store.mjs:395-405`), capped at 3 per use per session, and **a `host_reported` outcome may never supersede or follow a `user_marked` one** (amended after review, S1: enforced inside `withLock` as a predicate passed into `appendOutcome` at `store.mjs:372`, evaluated against the chain read under the lock, not in the MCP layer, so a concurrent CLI write cannot race it). (d) Ids are 128-bit, tickets capped at 64 outstanding, and issue/report rate limits apply (section 5). (e) A deleted use id is never re-registered (`judgeUse`, `store.mjs:328`).

**Why `register-uses` cannot be reused.** `registerReceiptUses` (`store.mjs:354`) accepts a complete `SkillUse` document with a caller-chosen `use_id`, skill identity and `issued_at` and checks only schema, the 90-day window and conflicts (`checkReceiptUse`, :343-348). Its trust comes from the caller being this machine's own engine writing its own receipt (`docs/skills.md:212`). Over MCP the caller is an untrusted agent: it could mint uses for skills it never fetched, with backdated times and any hash. The MCP path therefore never accepts a document; it accepts only an id the server issued and builds the row itself.

## 4. Evidence tiers and what needs the user

Tiers are the schema's: `verified | user_marked | host_reported | inferred` and `reported_by` `user | host | system` (`lib/skills/schemas/v1/outcome.schema.json:44-51`). `inferred` can only carry `unknown` and is never resolved (`record.mjs:42`).

**Rule (proposed).** Nothing is written without the user. The agent may, unprompted by the user: fetch a skill (in-memory ticket only), call `e3d_skill_record` and `e3d_my_calibration` (read-only). Everything that writes (`report_use`, `report_outcome`, `delete_outcome`) needs an explicit user act, enforced in two layers: the host's own permission prompt for a non-read-only tool (annotations above; whether Claude Code and Codex prompt is unverified, section 10), and a **server-initiated MCP elicitation** shown by the host (`bin/e3d-mcp` already uses one for the pipeline approval, `lib/mcp/pipeline-actions.js:82-93`). **Amended after review (B2):** the claim "an agent cannot answer an elicitation prompt itself" (`pipeline-actions.js:3-5`) is true of the model but not of the host: in Claude Code an `Elicitation` hook can answer without the user (https://code.claude.com/docs/en/hooks#elicitation), and in VS Code, desktop and `-p` mode elicitation is cancelled unless a hook accepts (https://code.claude.com/docs/en/mcp). That comment should be corrected in the same PR as P3-3. Consequences: the three write tools carry `_meta["anthropic/requiresUserInteraction"]: true` (https://code.claude.com/docs/en/mcp#require-approval-for-a-specific-tool) so Claude Code forces its own approval prompt; the docs say plainly that an `Elicitation` hook matching this server voids the meaning of `user_marked`; and cancel or any non-accept is a decline, so D1 stays a fail-closed floor (no answer, nothing written). The elicitation text is composed by Pilot from the ledger (skill id, version, hash; "stores identifiers and the result only, no task text"), never from agent-supplied text.

| Path | Result chosen by | Stored tier / reported_by |
|---|---|---|
| Host supports elicitation, user accepts and picks worked/failed/unknown in the dialog (agent's `result` is ignored, so no anchoring) | the user | `user_marked` / `user` |
| Host lacks elicitation, operator set `E3D_CALIBRATION_MCP_UNCONFIRMED=1` (D3) | the agent | `host_reported` / `host` |
| Host lacks elicitation, no opt-in | refused `skill_scope_denied`, nothing written | none |
| User declines or cancels | none | nothing written, no retry within 10 min |
| `verified` | not accepted over MCP in v1: no `evidence_ref` input exists (a digest the server cannot check would be self-asserted) | via CLI later |

Justification: a use or outcome the user never saw would poison the only thing the product sells (an honest record); over MCP `user_marked` is reserved for an accepted host-rendered elicitation (with the limits above); agent assertions are displayed as `host-reported` (`record.mjs:134`). **Amended after review (B1, honest limit):** the same label cannot be guaranteed on the CLI path, see C-T16 and the proposed TTY rule. Failing closed on hosts without elicitation costs capture volume, which the measurement plan (section 9) makes visible. `unknown` is first-class so a user can say "can't tell" without it counting as a failure.

**Elicitation discipline (amended after review, S3 and S6).** At most one pending elicitation per process; requests are serialised per `use_id`; a decline or cancel pauses all writes for 10 minutes. The delete dialog states the count and tiers of the outcomes it removes (`deleteOutcome` tombstones the whole chain, `store.mjs:408-418`), e.g. "removes 2 outcomes (1 user-marked, 1 host-reported) for skill.x 1.0.0". Skill ids, versions and `task_class` shown in dialogs and reads are fenced and labelled as data, never as text addressed to the user.
**Session means process (amended after review).** Claude Code subagents share the same MCP server process, so a subagent can use a ticket the parent fetched; the ledger's "session" is the process, not a conversation.

## 6. Privacy

Local store only: `~/.config/e3d-pilot/calibration/` (`E3D_CALIBRATION_DIR` override), dir 0700, files 0600, symlinks and foreign-owned or group-readable files refused (`docs/skills.md:171` section; `store.mjs` `checkDir`/`checkFd` :55-96). No network, no model call, no telemetry. **Never written:** task text, questions, answers, skill text, the agent's output, notes, file paths, the client's free-form fields, tool arguments (the server logs counts only, never arguments). **Allowlist.** Use row: `schema_version, use_id, skill{id,version,hash}, mode, host{family,model_family}, task_class, task_class_source, principal_ref, reminder_enabled, run_ref, issued_at, expires_at`; outcome row: `schema_version, outcome_id, use_id, result, tier, reported_by, evidence_ref (null in v1), supersedes, reported_at` (schemas `skill-use`, `outcome`, `additionalProperties:false`). Retention: uses and outcomes 365 days, ids 90 (`store.mjs:23-24`), applied by `--compact-calibration`. The agent's host sees what the read tools return (counts and ids) in its own context, which is the user's own choice of host; documented. `task_class` can re-identify at fine grain (C-T4); the docs say keep it coarse (D7).

## 7. The read tools' wording (ADR-0021)

Reuse `describeRecord` and `describeInsufficient` unchanged (`record.mjs:130-139`), so the sentence is the allowed shape: "in your 17 resolved uses, 12 were marked worked (approximate 95% interval 46% to 87%) ...; outcome sources: ... user-marked, ... host-reported; ... of uses were made with the reminder on; N corrections on file". Minimums: **10 resolved uses** per (skill, version, hash, task class, mode, model family) for any rate (`MIN_RESOLVED`, `record.mjs:15`), below it "not enough resolved outcomes (n of 10 needed)", counts only, no rate (`skill_record_insufficient` surfaced as a normal structured result, not a tool error). **30 per bin** (`BIN_MIN`, :16) is unreachable: no prediction capture, so `calibration` is null and `status` is `descriptive`. Every result carries a fixed notice: "A description of what you or your agent recorded. Outcomes are not checked by Pilot. It is not a claim that the skill improves results, and not a comparison with other skills or with no skill." **Mixed sources (amended after review, S2, decision D10).** Through MCP the agent can self-assert, so a rate built from `host_reported` outcomes would be self-grading. Chosen: the MCP read tools print a rate only when at least 10 of the resolved uses are `user_marked` or `verified`; otherwise they print counts and the source mix and say "not enough user-marked outcomes for a rate" (the CLI keeps `describeRecord` as it is, which already prints the source mix). Justification: it keeps the sentence honest without a new flag the agent could ignore; the alternative, a prominent "mixed sources, partly agent-reported" flag on every rate, is weaker because it is easy to skim past. This needs a small `describeRecord` option in P3-2, no schema change. Words banned by ADR-0021 (memory, learning, truth, audit, governance, "better outcomes", "improves", "best", "accurate", "verified" unqualified) are asserted absent by the shared copy test, extended to these tool descriptions and notices.

## 9. Measurement: the 15% kill criterion

Rule (spec section 9; ADR-0018 item 5, ADR-0016): stop expanding capture work if 60 days after this phase ships fewer than 15% of reported uses have an outcome. **Local counts only**; the owner's own machine and those of internal users, read by them, never uploaded. The literal denominator ("reported uses") is biased high here, because a use row exists only when someone chose to report it. So P3-5 adds a counts-only file (`tickets.jsonl`: day, tickets issued, uses persisted; 0600, no ids) and `e3d-debate --calibration-rate` prints: A = uses with a current resolved or unknown outcome / uses persisted (the literal rule); B = same / tickets issued (conservative); n, a Wilson interval (`wilsonExact`, `record.mjs:25`), and the window start. **Amended after review:** outside the interactive terminal Claude Code cancels elicitation (VS Code, desktop, `-p`) unless a hook accepts, and Codex auto-rejects elicitation by default, so recording there will be close to zero and says nothing about willingness to record. The 15% criterion is therefore measured on **interactive-terminal tickets only**: the ticket counter stores a coarse `surface` (`interactive` when the host advertised elicitation, else `other`; an enum, no free text) and rates A and B use `interactive` tickets only. Decision at day 60 is the owner's; below n=30 tickets it prints "too few to decide". It must never prompt anyone to raise the number.

## 10. Owner decisions (default in parentheses) and open questions

- **D1** Writes need a server-side elicitation the agent cannot answer; no write without it (default: yes).
- **D2** Over MCP only `user_marked` (elicited) and `host_reported` exist; no `verified` and no `evidence_ref` in v1 (default: yes).
- **D3** Hosts without elicitation: refuse writes, with an operator opt-in `E3D_CALIBRATION_MCP_UNCONFIRMED=1` that stores `host_reported` only; deletion never unconfirmed (default: refuse unless opted in).
- **D4** `use_id` lives in memory until the user permits recording; fetch alone writes nothing (default: yes).
- **D5** No opt-in reminder text in tool descriptions in v1; `reminder_enabled` stays false (default: defer to a later PR).
- **D6** Ticket lifetime 24 hours in-session; later reports only by CLI on a persisted use (default: 24 h).
- **D7** `task_class` stays a free slug the agent may declare, documented as "keep it coarse"; a closed vocabulary is a later option (default: free slug).
- **D8** `e3d_my_calibration` readable by the agent without asking the user, aggregate only (default: yes; alternative is elicitation per read).
- **D9** Add the counts-only `tickets.jsonl` for the 15% rule, with the `surface` enum (default: yes).
- **D10** (amended after review) MCP reads print a rate only with at least 10 user-marked or verified resolved uses; otherwise counts and source mix only (default: yes; alternative: a mixed-source flag).
- **D11** (amended after review) a separate `E3D_CALIBRATION_MCP=1` switch for the MCP tools, beyond `E3D_CALIBRATION_V1` (default: yes).
