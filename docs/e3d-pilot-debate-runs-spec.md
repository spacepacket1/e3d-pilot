# Hosted debate runs: async tools, a run store, record and fetch hook calls, and pre-reserved internal runs

## Overview

A debate takes minutes. Over the hosted HTTP transport the current `e3d_debate` tool is one long request with no progress, so a
client that gives up early (Claude Code stops waiting at about 60 seconds; chat clients are often stricter) drops the answer
while the server finishes the debate and settles the charge: the customer pays and never sees the result. Verified locally on
2026-10-18 with a 90 second debate. This ticket makes debates durable, retrievable runs: connectors can start a debate and
fetch it later, every finished debate is handed to the billing service to be saved (transcripts are saved), and the hosted
server can execute a debate that the billing service has already reserved (used by the pilot.e3d.ai web page). Everything is
off unless the external auth hook is configured; the existing synchronous `e3d_debate`, stdio and static-token modes keep
working unchanged.

## Decisions

- **D1. New customer tools** (hook and HTTP mode only, added to the default customer allowlist next to `e3d_debate`,
  `e3d_list_providers`, `e3d_usage`): `e3d_debate_start` (same arguments as `e3d_debate`; returns `{debate_id,
  status:"running", poll_after_sec}` as soon as the reservation is held and the run is queued), `e3d_debate_status
  {debate_id}`, `e3d_debate_result {debate_id, include_transcript}`. The synchronous `e3d_debate` stays, and also records.
- **D2. A debate id** is `dbt_` plus 24 lowercase hex characters, generated by the server (the web page may supply one that the
  billing service generated). A principal can only read its own debates: every lookup is keyed by the principal that
  introspection returned; an unknown id and someone else's id answer identically (`not_found`).
- **D3. Metering is unchanged in meaning.** `start` performs `begin` (reserve) before it returns and the run settles through the
  same `commit` path as the synchronous tool, so the intent, orphan policy, outbox and local-counter behaviour from the hook
  epic all apply. A refused reserve (no credits, suspended, busy) is returned from `start` directly as the same tool error as
  today. The debate id is the metering `request_id`.
- **D4. Run store.** Per-run state in the server's state directory, `runs/<safe principal>/<debate_id>/` with `state.json`
  (status `queued|running|done|failed`, timestamps, arguments, usage, outcome, billing fields) and `transcript.md`; written
  atomically (temp file then rename), mode 0600 in 0700 directories, bounded by a TTL (default 24 hours; the durable copy is the
  billing service's) and a per-principal cap (default 50 runs; the oldest finished runs are removed first). Question and answer
  text never appear in logs.
- **D5. Concurrency.** At most `E3D_MCP_RUNS_PER_PRINCIPAL` (default 3) and `E3D_MCP_RUNS_GLOBAL` (default 8) runs execute at
  once; a further `start` is refused with a clear `busy` tool error before anything is reserved.
- **D6. `record` hook call (optional, durable).** After a run or a synchronous debate finishes and its settlement is decided,
  the server delivers `record` to the billing service through the outbox (a new record type next to `settle` and `release`,
  idempotent per `reservation_id`): `{reservation_id, debate_id, source:"connector"|"web", question, providers, rounds,
  outcome, result:{final_answer, consensus, dissent, positions[]}, usage, transcript}` with a 512 KB cap on the whole body
  (a larger transcript is truncated at a section boundary and marked). It is sent only when the service advertises support
  (D8). A service that answers `not_found` or `invalid` dead-letters the record like any other permanent answer.
- **D7. `fetch` hook call (optional).** `e3d_debate_status` and `e3d_debate_result` read the local store first; when the run is
  not local (expired, or the server restarted and lost memory of it) and the service advertises support, the server asks the
  service `fetch {debate_id}` (the service checks the principal) and returns what it holds.
- **D8. Capability advertisement.** `introspect` responses may carry `features:["record","fetch","run"]`; the server only uses
  what is listed. A service that lists nothing works exactly as before.
- **D9. Pre-reserved internal runs.** When `E3D_MCP_RUN_PORT` and `E3D_MCP_RUN_TOKEN` (32+ characters) are set, a second listener
  on 127.0.0.1 only accepts `POST /internal/runs {reservation_id, debate_id, principal, question, providers?, rounds?,
  max_words?, source}` and `GET /internal/runs/{debate_id}`, authenticated by that token in constant time. The server builds a
  metering handle from the existing reservation (no new reserve), runs the debate with the same limits, settles and records. A
  duplicate `debate_id` returns the existing run. It never exposes the run listener through the public listener.
- **D10. Interrupted runs.** On restart a run found `running` is marked `failed` with reason `interrupted`; its intent is handled
  by the existing orphan policy (a run that never started its models is released, one that did is charged or released per
  `E3D_MCP_ORPHAN_POLICY`), and the record call is attempted with outcome `error`.
- **D11. Docs and conformance.** `docs/external-auth.md` documents `features`, `record` and `fetch` (requests, responses, size cap,
  idempotency, error codes); the stub service and conformance runner implement and test them.

## Goals

- A client with any timeout can run a debate: start, poll, fetch, and never lose a paid result.
- Every finished debate reaches the billing service for storage without blocking the customer.
- The web page can run a pre-reserved debate on the same engine and limits as connectors.

## Non-Goals

- Storing transcripts in this repository's server beyond the short local TTL, any UI, OAuth, pricing, or retention policy
  (the billing service owns all three).
- Changing the stdio or static-token behaviour, the pipeline tools, or the sync `e3d_debate` contract.

- `lib/mcp/http.js`, `lib/mcp/metering.js`, `lib/mcp/outbox.js`, `lib/mcp/external-auth.js`, `lib/mcp/usage.js`, `lib/mcp/jobs.js`

- `docs/external-auth.md`, `docs/external-auth/*` (schemas and vectors), `examples/external-auth-stub.js`,

- `tests/mcp-extauth.sh`, `tests/fixtures/extauth-*.mjs`, `tests/mcp-http.sh`: test style (stub debate binary, throwaway state
  dirs, stub service, no real models).

## Shared Constraints

- Zero new dependencies. Nothing is logged that contains a question, an answer, a transcript, a key or a token.
- Everything new is inert without the hook; default behaviour of every existing mode and tool is byte-for-byte unchanged
  (the existing test scripts must still pass without modification except where a phase says otherwise).
- All new state is crash-safe: temp file plus rename, fsync where the existing code does, no partial JSON ever visible.
- The tool descriptions are written for people who are not developers: "start a debate", "check on a debate", "get the result".

## Phase 1: Run store and the async tools

Add `lib/mcp/runs.js` (the store, runner, limits, TTL and cap, interruption recovery, per-principal isolation) and the three
tools in `bin/e3d-mcp`, reusing the sync debate's argument validation, worst-case estimate and `metering.begin/start/commit`.
`e3d_debate_start` returns after `begin` succeeds and the run is queued; the runner reuses the debate execution code from
`toolDebate` (refactor it into a shared function without changing its behaviour). `e3d_debate_status` and `e3d_debate_result`
read the store and are rate-limited by the existing per-principal limits. Add the three tools to the hook-mode customer
allowlist and `--doctor` output.

## Phase 2: The record and fetch hook calls

Extend `lib/mcp/external-auth.js` with `record` and `fetch` (timeouts, redirect refusal, size caps, schema validation, the
`features` field from `introspect`), `lib/mcp/outbox.js` with the `record` record type (idempotent per reservation id, the 512 KB
body cap with section-boundary truncation, dead-letter on permanent answers, retention under the existing outbox bound rules),
the call sites in the sync tool and the runner (enqueue after the settlement decision, never blocking the reply), the `fetch`
fallback in status and result, the stub service and the conformance runner (new vectors), the JSON schemas and
`docs/external-auth.md`.

## Phase 3: Pre-reserved internal runs

Add the loopback run listener (`lib/mcp/run-server.js`): token check, strict body validation, the metering handle built from an
existing reservation, idempotence on `debate_id`, progress and result on `GET`, and its start-up and shutdown wiring and
`--doctor` entry. It reuses the Phase 1 runner and the Phase 2 record path with `source:"web"`.
