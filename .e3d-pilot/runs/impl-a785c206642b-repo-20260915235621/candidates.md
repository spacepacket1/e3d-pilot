# Candidates

## Proposed Candidates

### Candidate 1: Add opt-in Gemini CLI provider adapter for e3d-debate trial
Duplicate: no
Dedup rationale: This idea did not exist before this debate. Verified via `e3d-pilot ideas list` conventions (grep for any prior Gemini-related idea) that no existing idea in this repo's .e3d-pilot/ideas/ ledger covers a Gemini adapter; the only prior related history is the e3d-graph-generalization and hugging-face-strategy debates, which are unrelated topics. This idea is the direct, single, converged output of a real e3d-debate run on 2026-09-15 (docs/debates/2026-09-15-gemini-qwen-provider-addition/transcript.md, full consensus across claude/codex/devin/grok-build after 3 rounds), not a rediscovery of prior work.
Category: provider-integration
Analogy: Same shape as the existing grok-build adapter (docs/debates history shows grok-build was added the same way: one contract-compliant script, opt-in via explicit provider naming, no default-config change) -- this is that same pattern applied to a fourth foundation-model family that the repo's own e3d-debate concluded fills a real diversity gap (Devin defaults to a Claude model, so today's panel is really three families, not four).
Attraction (1-5): 4
Retention (1-5): 3
Effort: small
Revenue (1-5|n/a): n/a
Description: Add lib/providers/gemini, a new provider adapter built strictly to the existing lib/providers/<name> contract (same shape as lib/providers/claude, lib/providers/codex, lib/providers/devin, lib/providers/grok-build, sharing lib/providers/common.sh). This is scoped exactly to the recommendation from the e3d-debate transcript at docs/debates/2026-09-15-gemini-qwen-provider-addition/transcript.md (full consensus, all 4 participants, 3 rounds): build a minimal Gemini CLI adapter at claude-grade telemetry, for an opt-in trial in e3d-debate only. Do NOT add Qwen3 Coder or an OpenRouter adapter (rejected unanimously in that debate: paid-only, no free tier, coder-specialized, duplicates the already-existing lib/providers/local adapter). Do NOT change any default in .e3d-pilot/config.json or bin/e3d-debate's default --providers (which stays claude,codex) -- Gemini is invoked only via an explicit --providers flag naming it. Do NOT make Gemini the debate synthesizer. Do NOT list Gemini in any e3d-pilot pipeline stage (discover/ideate/draft/negotiate/execute/review) in config.json -- the debate's specific finding was that negotiate fails the entire run if a listed reviewer is unavailable, and Gemini's free-tier daily quota is shared account-wide with any other Google/Gemini usage and can be exhausted unpredictably with no dollar-cap-style warning, which is incompatible with being a required pipeline participant.

Required shape for lib/providers/gemini, following the pattern already established in lib/providers/codex and lib/providers/grok-build:
- GEMINI_BIN (default 'gemini') and GEMINI_MODEL (env var override, no forced default beyond whatever the CLI itself defaults to) for explicit model selection, matching how CODEX_MODEL/DEVIN_MODEL/GROK_BUILD_MODEL already work.
- E3D_PILOT_CHECK=1 support: prints an availability line and exits 0 (available) or 2 (unavailable) without invoking the real binary, matching every existing adapter's provider_binary_available check.
- E3D_PILOT_DRY_RUN=1 support: prints the exact command that would run (including the prompt file path) without calling the real binary, matching every other adapter.
- Reads the prompt from the required $1 prompt-file argument via provider_require_prompt_file, matching every existing adapter -- never inline text on argv.
- Invokes the gemini CLI in fully non-interactive/headless mode (its own --non-interactive / --prompt-from-file-equivalent flag per the CLI's own headless-mode docs) with JSON output format, reading the prompt file's content as the single prompt. Never pass --yolo or any auto-approve-tool-execution flag -- tools must stay off/unused for this adapter, the same posture lib/providers/codex and lib/providers/grok-build already take in their analysis mode (CODEX_SANDBOX_MODE=read-only, GROK_BUILD_MODE=analysis with no --disable-web-search override needed here since Gemini CLI tool-use should simply never be invoked for this adapter's use case of answering a self-contained debate prompt).
- Wrap the real invocation in provider_run_with_timeout from lib/providers/common.sh (a GEMINI_TIMEOUT env var, reasonable default e.g. 120 seconds, matching LOCAL_MODEL_TIMEOUT's pattern) so a hung call cannot block a debate round indefinitely.
- Enforce a hard, pre-call, per-invocation request ceiling is not meaningful for a single prompt-in/response-out call (there is only ever one request per invocation), so the meaningful safeguard is: (a) the timeout above, and (b) a hard token/output-size ceiling analogous to codex/claude's PROVIDER_TOKEN_LIMIT pattern, enforced post-hoc by failing the call (exit 1) if the CLI's own reported token usage (parsed from its JSON output) exceeds a configurable ceiling (e.g. GEMINI_TOKEN_LIMIT, default matching the existing PROVIDER_TOKEN_LIMIT default of 200000).
- After every real call, print exactly one usage line to stderr in the same shape the claude adapter already uses: e3d_provider_usage={"provider":"gemini","model":<exact model string reported by the CLI response, never a hardcoded guess>,"tokens":<total token count from the CLI's own reported usage>,"cost_usd":0} -- cost_usd must be the literal 0 only when the call used the free OAuth path; if the adapter cannot positively confirm the free OAuth path was used (e.g. a paid API key or Vertex AI credential path is configured instead), it must NOT claim cost_usd:0 -- either report unmeasured:true (matching the claude adapter's own fallback pattern for non-JSON responses) or fail closed rather than silently under-report a real cost. Never invoke any paid/billed Gemini authentication path automatically -- if only paid credentials are configured and no free OAuth session exists, the adapter should fail with a clear error (exit 1) rather than silently spend money, since this ticket's whole premise is using the free tier.
- If the CLI's JSON response includes an exact model/version string (not just a family name like 'gemini'), extract and print it in the usage line so debate transcripts can distinguish which underlying model actually answered -- this directly closes a gap the debate transcript flags: e3d-debate currently records only the provider name ('gemini'), never the exact model/version, which the debate concluded is necessary before any trial result can be trusted (a thin free-tier model masquerading as 'Gemini' would otherwise look identical to a strong one in the transcript).
- Exit codes: 0 success, 1 failure (binary present but the call errored, including the fail-closed cases above), 2 unavailable (binary not found, matching every existing adapter's contract), consistent with the documented contract at the top of lib/providers/common.sh.

Also required: a new tests/phase<N>.sh (next available number after the current highest, tests/phase33.sh, so tests/phase34.sh) covering, using a stub gemini binary the same way existing provider tests stub codex/claude/devin binaries: E3D_PILOT_CHECK=1 reports available/unavailable correctly; E3D_PILOT_DRY_RUN=1 prints the expected command without invoking the stub; a normal successful call returns the stub's response text and emits a correctly-shaped e3d_provider_usage line including provider, model, tokens, and cost_usd:0; a simulated over-token-limit response causes exit 1; a missing-binary case exits 2; and bin/e3d-debate itself can successfully run a 2-provider debate naming 'gemini' via --providers when the stub is present (proving the adapter is a drop-in participant with no changes needed to bin/e3d-debate itself, since that script already generically shells out to any lib/providers/<name> matching the name passed to --providers).

Also required: extend README.md's existing 'Providers and negotiation' section with a short new paragraph documenting the gemini adapter exactly the way the existing grok-build paragraph is documented (env vars, install/auth pointer, explicit statement that it is opt-in only -- not part of any default config.json providers.* value and not part of bin/e3d-debate's own default --providers -- and that it exists specifically to be named explicitly via --providers for e3d-debate trials, per the linked debate transcript). Do not add Gemini to any example config.json snippet in the README that currently shows default/recommended provider settings.

Non-goals for this idea, explicitly: no Qwen3 Coder adapter, no OpenRouter adapter, no lib/providers/local changes, no config.schema.json changes, no .e3d-pilot/config.json changes, no bin/e3d-debate default-provider changes, no synthesizer role for gemini, no wiring gemini into any e3d-pilot pipeline stage. The actual trial (re-running two historical docs/debates/ questions with --providers claude,codex,gemini and scoring keep/kill) is explicitly out of scope for this implementation ticket -- it is a manual follow-up step to run after this adapter lands, not code to write here.
